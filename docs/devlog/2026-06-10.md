# Devlog — 2026-06-10

Session focused on running a Chaosify pentest against the local `minikube` cluster,
independently verifying the results, and investigating two accuracy gaps that surfaced.
Net code/skill change for the day is small: **one notice added, everything else reverted.**
This log records what we did and — importantly — *why* the bulk of it was rolled back.

---

## 1. Ran a pentest on `minikube` (via the `chaosify` skill)

- Confirmed authorization, ran `setup init` + `preflight`, then the full recon survey.
- Ran the `preventive-baseline` pack plus targeted manifest/network/identity/detect probes.
- Produced a report: overall posture **High** — admission control (Kyverno, 6 Enforce
  policies) strong in `chaosify-tests`; gaps in image policy (latest-tag,
  unapproved-registry), no NetworkPolicies (open egress), no runtime detection.
- Artifacts under `.chaosify/runs/2026-06-11T00-23-00Z/`.

## 2. Independent verification with `kubectl`

- Cross-checked every finding using `kubectl`, server-side dry-run admission, and
  `kubectl auth can-i` (no Chaosify CLI).
- Wrote the analysis to `docs/accuracy-gaps-minikube.md`.
- Found **two wrong conclusions** and **three missed findings**. Two became the focus of
  the rest of the session (below).

---

## 3. Problem 1 — RBAC recon missed a `cluster-admin` ServiceAccount

**The gap:** `recon rbac` reported only the `kubeadm:cluster-admins` *Group* binding and
missed `kube-system:default` being bound to `cluster-admin` (the well-known `minikube-rbac`
default) — the more dangerous, since a SA token is reachable from any pod.

**Root cause (in `core/recon/rbac.ts`):**
- `includeSystem` defaults to `false`, and `SYSTEM_NAMESPACES` includes `kube-system`, so
  the only subject of `minikube-rbac` was filtered out → the finding collapsed to nothing.
- Even when shown (`--include-system`), a ServiceAccount cluster-admin is rated only `WARN`.

**What we changed (skill-level):** made `recon rbac --include-system` the default for
pentests, added denoising guidance (distinguish literal `cluster-admin` from scoped
`system:controller:*` roles), and added hypothesis rows for SA→cluster-admin. Applied
across `claude`, `agentic-pentest` (SKILLs + cli-reference) and `codex`.

## 4. Problem 2 — Namespace-scoped probing / exempt-namespace blind spot

**The gap:** the report concluded "node escape is blocked," but all 6 Kyverno policies
`exclude` `kube-system` (+ `kube-public`, `kube-node-lease`, `kyverno`). A privileged +
`hostPath:/` pod is admitted there (verified via dry-run). Combined with the
`kube-system:default` cluster-admin SA from Problem 1, that's a full node-takeover chain.

**Root cause (in `core/recon/policies.ts`):** `probeKyverno` maps each policy to only
`{ name, engine, validationFailureAction }` and **discards `spec.rules[].match`/`exclude`**.
So the namespace exemptions are never surfaced, and the "all policies actively blocking"
INFO message is misleadingly reassuring. Probes also only default to `chaosify-tests`
(though `--namespace` *can* override — the binary is not actually locked to one namespace).

**What we changed (skill-level):** added hypothesis rows for "policy excludes a namespace →
node-escape chain" and a reminder that Chaosify only probes `chaosify-tests` by default.

---

## 5. Decision: revert all of Problems 1 & 2 skill edits

After discussion, the maintainer decided **not** to keep the Problem 1/2 skill changes, and
to revert everything from the session. Reasoning:

- **The `--namespace` override already exists.** Every probe command accepts
  `--namespace`, so an operator can already test `kube-system` (or any namespace) directly.
  Surfacing exemptions in recon was judged not worth the added complexity/noise.
- **Exemptions are normal.** Excluding `kube-system` from admission policies is standard
  and intentional (system components legitimately need privileged pods). The exemption
  itself is not a defect — only an unguarded *and* attacker-reachable namespace is, and
  that judgement is left to the operator.
- **Accepted tradeoff:** discoverability stays manual. The skill guidance we added was
  effectively toothless anyway without a recon change feeding it the exemption data, so the
  skill edits added wording without real capability.

**Reverted:** all session edits to `claude/SKILL.md`, `agentic-pentest/SKILL.md`,
`agentic-pentest/references/cli-reference.md`, `chaosify/references/cli-reference.md`, and
`codex/SKILL.md` — including the Problem 1 `--include-system` RBAC changes. Verified no
traces remain. Pre-existing `[--include-system]` flag listings (not ours) were left intact.

**Not reverted:** `docs/accuracy-gaps-minikube.md` — it was an explicit deliverable, not a
skill edit. (It still contains the Problem 1/2 analysis and the "structurally blind"
wording, which slightly overstates the binary's limitation; left as-is pending a decision.)

## 6. Kept: namespace-transparency notice

In place of the reverted work, added a notice to the **confirmation step** so the agent
tells the user up front that Chaosify creates its **own dedicated namespaces** (`chaosify`
for setup/runner, `chaosify-tests` for test workloads), separate from their application
namespaces, with all test pods namespace-scoped and auto-cleaned.

- Added to the 3 skills that create namespaces: `claude/SKILL.md`,
  `agentic-pentest/SKILL.md`, `chaosify/SKILL.md`.
- **Not** added to `codex/SKILL.md` — it is a pure knowledge reference that runs no commands
  and creates no namespace, so the notice would be false there.
