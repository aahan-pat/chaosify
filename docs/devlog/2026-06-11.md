# Devlog — 2026-06-11

Session focused on `recon rbac`. Started as a walkthrough of the existing RBAC checks,
turned into a real capability change: the tool now emits a **subject-centric RBAC
knowledge graph** for the agentic layer, covers namespaced RBAC, and a **false-positive
class was found and fixed** while verifying output against `minikube`. Net change is
additive and shipped (built + reinstalled globally). Two bugs remain open (below).

---

## 1. Reviewed the RBAC recon surface

Walked `core/recon/rbac.ts`. It emitted exactly **four** findings: cluster-admin bound to
a non-system principal (HIGH for Group/User, WARN for SA), per-SA cluster-wide secret read
(HIGH), and two 403→SKIP notices. Scope was **cluster-level only** (`listClusterRole` /
`listClusterRoleBinding`); namespaced `Role`/`RoleBinding` were never read. Only two attack
patterns were detected — everything else (exec, escalate/bind, impersonate, rbac-write,
token mint, …) was invisible.

## 2. Decision — emit knowledge, not just verdicts

`ReconToolResult.data` was already documented as *"raw structured data for agentic AI
consumption"* but RBAC only put three counts there. Decided to fill it in with a real
graph rather than keep hand-coding heuristics (combinatorial escalation chains are what the
LLM is good at; the heuristic treadmill is not). Kept the 4 heuristic findings as cheap,
deterministic anchors for non-LLM consumers (CI, human scan) — **graph in addition to, not
instead of, findings**.

**Implemented:**
- `src/types/recon.ts` — `RbacGraph` / `RbacSubjectNode` / `RbacEffectiveRule` / `RbacScope`
  and a 12-value `RbacCapabilityTag` union.
- `core/recon/rbac.ts`:
  - `tagRule()` — annotates each rule with sensitive-capability hints (secret-read,
    pod-exec, pod-create, workload-write, rbac-write, escalate, bind, impersonate,
    token-create, wildcard-verb/-resource, cluster-admin). Hints, not verdicts.
  - `buildGraph()` — resolves every binding→role (cluster **and** namespaced), pre-joins
    rules onto each subject, collapses multi-binding grants onto one node, scopes
    RoleBindings to their namespace, rolls tags up into a per-subject `capabilities`
    summary, filters `system:` / system-namespace principals (honors `includeSystem`,
    counts omissions), and caps size (`MAX_SUBJECTS=200`, `MAX_RULES_PER_SUBJECT=60`,
    most-privileged first, with a `truncated` flag).
  - `surveyRbac()` — now also lists namespaced `Role`/`RoleBinding` (each with its own
    403→SKIP finding) and returns `data.graph` + `roleCount`/`roleBindingCount`. Existing
    `data` fields untouched.
- `cli/commands/recon/rbac.ts` — table now prints Roles/RoleBindings scanned and "Subjects
  mapped in RBAC graph: N (truncated)".

Note: the type was `RbacV1Subject` in `@kubernetes/client-node` 1.4 (not `V1Subject`).

## 3. Build/run loop gotcha (cost real confusion)

After editing source, `chaosify recon rbac` showed **no change**. Cause was two-fold:
(a) the CLI is bundled by `tsdown` into a single `dist/index.js` and the source was never
rebuilt; (b) the `chaosify` on PATH is a **copied global install** at
`~/.local/lib/node_modules/chaosify-kubernetes/`, *not* a link to the working tree — so even
a fresh build wouldn't reach it. Fixed by `npm run build && npm install -g .`. Recorded the
loop in agent memory. Fast iteration without reinstall: `npm run dev -- <args>` (tsx on src).

## 4. Verification on `minikube` → found and fixed an apiGroup false positive

Ran `--include-system` and cross-checked the graph (dumped via `--output`, which is
truncation-safe). Default scope: 1 subject (`kubeadm:cluster-admins`) + 75 system omitted —
correct. `--include-system`: 60 subjects.

**Bug found:** `horizontal-pod-autoscaler` was flagged HIGH for cluster-wide secret read.
Its triggering rule was `apiGroups:["custom.metrics.k8s.io"], resources:["*"]`. secrets are
in the **core** group (`""`), so a wildcard resource in the metrics group does **not** grant
them. The detector — both the original `analyze()` heuristic **and** the new `tagRule()` —
checked `resources`/`verbs` but **ignored `apiGroups`**, so `resources:["*"]` in *any* group
falsely matched core resources. This blind spot predated this session; it lived in
`hasClusterWideSecretRead` from the start and only surfaced because the graph made us look.

**Fix:** introduced `covers(resource, owningGroup)` requiring both the resource (or `*`)
**and** the owning apiGroup (or `*`). Applied to every resource-scoped tag, killing a whole
class of false positives (e.g. `deployments` under the core group no longer counts as
workload-write), plus the same group check in `analyze()`'s secret-read heuristic. After
fix + reinstall, the HPA finding is gone; the four true positives (default SA cluster-admin,
generic-garbage-collector, namespace-controller, resourcequota-controller — all genuine
`apiGroups:["*"]` wildcards) remain.

## 5. Tests

Extended `test/unit/core/recon/rbac.test.ts`: graph-building (tagging, scope, multi-binding
collapse, system filtering, truncation) + apiGroup regression tests (non-core wildcard not
flagged; workload-write only when the group owns the resource). **30 tests pass**, typecheck
clean, build + global reinstall verified to carry the fix.

## Open items / follow-ups (not done today)

- **Piped-JSON truncation bug (diagnosed, NOT fixed).** `recon rbac --format json | …` is
  cut at exactly 64 KB (the pipe buffer). Cause: the command does
  `console.log(JSON.stringify(...))` then `process.exit(0)` immediately — on a pipe, stdout
  is async and exit kills it before flush. `--output file.json` (sync fs write) is
  unaffected. Almost certainly affects the other seven recon commands (same pattern). Fix:
  set `process.exitCode = 0` and return instead of `process.exit(0)`.
- **Heuristic findings still cluster-only.** Namespaced RBAC feeds the graph but not the
  HIGH/WARN findings. Extending `analyze()` to namespaced grants is separate.
- **No `recon all` aggregator.** The `ReconReport` type still promises a unified sweep that
  no command assembles — each tool's graph lives only in its own `data`.
- **Graph not yet wired into the agentic skill prompt** — the consumer that motivated this
  work still reads findings, not `data.graph`.
